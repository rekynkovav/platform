# Правила работы мультиагентной системы OpenCode

## Режим работы
По умолчанию ВСЕ задачи проходят полный цикл.
Исключение: тривиальные задачи (однострочные исправления, опечатки).

## Принципы (перед циклом)

### Технологическая нейтральность
- Архитекторы и критики **не привязаны** к конкретному стеку.
- Стек определяется **скаутами** на основе анализа проекта.
- Архитекторы получают готовую сводку, но **могут сами пойти почитать** проект.

### Правило возврата
- **Любое обоснованное замечание** → возврат к источнику:
  - Замечание архитектору → архитектор переделывает план.
  - Замечание кодеру → кодер переделывает код.
- Замечание **без доказательства** = недействительно.
- При возврате критик указывает **ТОЛЬКО** новые ошибки.

### Железное правило цикла
- **Каждый этап ОБЯЗАТЕЛЕН:** Скауты → Архитекторы → Критики → Кодеры → Рецензенты → Аудитор.
- **Запрещено** пропускать Архитекторов или Критиков и идти сразу к Кодерам.
- **Запрещено** запускать Кодеров без утверждённого плана от Архитекторов + Критиков.
- Нарушение = немедленный возврат к Шагу 1 (Архитекторы).

## Цикл выполнения

### Шаг 0: Оркестратор
- Разбивает задачу на N подзадач.
- Запускает скаутов.
- Спавнит controller subagent для MEDIUM+ задач.

### Шаг 1: Скауты (3-5 шт.) — параллельно
- Каждый скаут изучает СВОЮ часть проекта:
  - Стек и зависимости (pom.xml, package.json, etc.)
  - Структура модулей и пакетов
  - Ключевые файлы и их назначение
  - Существующие паттерны и архитектура
  - Текущие проблемы (из логов, git history)
- Формируют **сухую сводку**: факты, без решений.
- Архитектор **может** пойти и сам почитать файлы.

### Шаг 2: Архитекторы (3-5 шт.) — параллельно
- Получают сводку от скаутов + задачу.
- **Могут сами обратиться к файлам** проекта для уточнения.
- Формируют решение с обоснованием (файл:строка + логика/спецификация).
- Отвечают строго на русском.

### Шаг 3: Критики (3-5 шт.) — параллельно, по одному на архитектора
- Каждый критик проверяет решение СВОЕГО архитектора.
- **Правило доказательства:** Что + Где + Почему + Как исправить.
- **Вердикт:**
  - УТВЕРЖДЕНО → на слияние.
  - ВОЗВРАТ → архитектору с конкретным списком ошибок.
- Макс **3 раунда** спора.

### Шаг 4: Слияние (Оркестратор)
- Собирает все утверждённые решения.
- Разрешает конфликты.
- Формирует единый итоговый план.

### Шаг 5: Кодеры (3-5 шт.) — параллельно
- Каждый кодер реализует СВОЮ часть плана.
- Стек и подходы из плана архитекторов.
- Используют относительные пути и Docker-команды.

### Шаг 6: Рецензенты (3-5 шт.) — параллельно
- Каждый рецензент проверяет СВОЮ часть кода на соответствие плану.
- **Правило доказательства:** Что + Где + Почему + Как исправить.
- **Вердикт:**
  - УТВЕРЖДЕНО → код передаётся аудитору.
  - ВОЗВРАТ → кодеру с конкретным списком ошибок.
- Макс **3 раунда** спора.

### Шаг 7: Аудитор
- Запускает тесты параллельно:
  - Unit-тесты
  - Integration-тесты
  - Security-скан
  - Build-проверка
- При ошибках → возврат на Шаг 6.
- Подтверждает готовность к коммиту.

## Формат доказательства (обязателен для всех агентов)
Каждое утверждение «X — ошибка / проблема / уязвимость» должно содержать:
- **Что:** описание проблемы
- **Где:** файл:строка или код
- **Почему:** логика/спецификация
- **Как исправить:** предложение

Без всех 3 компонентов замечание игнорируется.

---

## Формат сводки скаута
Каждый скаут предоставляет:
- Тип проекта (monolith, microservices, library)
- Язык и фреймворк
- Стек (БД, кэш, MQ, etc.)
- Структура модулей (список ключевых пакетов/файлов)
- Зависимости (ключевые библиотеки)
- Существующие паттерны (design patterns, архитектурные решения)
- Известные проблемы (баги, TODO, deprecated)
- Связи между модулями

## 7 РЕФЛЕКСОВ ИСПОЛНЕНИЯ (добавлено 2026-06-12)

```
R1. GRPO-LOOP — перед КАЖДЫМ значимым решением генерируй 3 варианта.
    Не только на старте. GRPO на: выбор subagent, verification method, synthesis approach.
    Без GRPO = решение невалидно.

R2. AUTO-COMPRESS — контекст >50% → сожми НЕМЕДЛЕННО.
    Качество падает за 50%. Компресс перед каждой новой волной, перед финальным выводом.

R3. CONTROLLER — MEDIUM+ ВСЕГДА создаёт controller subagent.
    Controller аудитит utilisation, размер контекста, timing, нарушения.

R4. WAVE-3 — COMPLEX ВСЕГДА требует Wave 3 (integrator + adversarial).
    Свежий контекст, атака на свои выводы, cross-cutting themes.
    Wave 3 опциональна = будет пропущена в 90% случаев. Только mandatory.

R5. POST-TASK COMPLETE — все 6 шагов post-task-protocol, самоинициировано.
    Reflection → memory → skill update → git-sync → self-check.
    Никогда не завершай задачу не закрыв цикл.

R6. MICRO-REFLECTION — после КАЖДОГО tool call.
    [REFLECT] micro | quality:Y/N | tool_right:Y/N | need_more:Y/N | switch:Y/N
    2 секунды. Предотвращает инерцию инструментов.

R7. PARALLEL WORK — НОЛЬ времени простоя после делегирования.
    Subagent бежит → я работаю. Планирую волну, читаю references, анализирую результаты.
    Idle = FAILURE.
```

Оставлять:
- Суть задачи и финальные решения

- Правила из AGENTS.md + 7 рефлексов
- Активный чеклист с ✅/⏳

## Уроки сессий (важно для будущего)

### Docker
- **Кеш слоёв:** При изменении исходников Docker может использовать кешированные слои. Решение: `BUILD_DATE=$(date +%s) docker compose build --no-cache` или `--build-arg BUILD_DATE=...`.
- **Дублирование Dockerfile:** Если есть два Dockerfile для одного сервиса — убедиться, что docker-compose ссылается на правильный.

### Фронтенд
- **Дублирование файлов:** Если есть App.js И App.tsx — webpack возьмёт .js. Удалить дубликаты.
- **Импорты:** При восстановлении старых компонентов — ПРОВЕРЯТЬ все import/export. Missing import = runtime error.
- **Browser cache:** После изменения JS всегда делать Ctrl+Shift+R.
- **CSP:** Каждый новый внешний домен (API, Keycloak) добавлять в connect-src/frame-src.
- **Keycloak iframe:** `checkLoginIframe: false` отключает 3rd-party cookie check (решает CSP iframe ошибки).

### Git
- **Ветки:** Старые ветки содержат полный функционал. При потере — искать в `git log --all -S "текст"`.
- **Восстановление:** `git show ветка:путь/к/файлу > файл` для извлечения старых версий.

### Рантайм ошибки
- **Build OK ≠ Working OK.** Build проверяет синтаксис, но не рантайм.
- **ErrorBoundary** ловит ошибки но не показывает. Нужно добавить `console.error` в `componentDidCatch`.
- **Минификация:** В production bundle имена переменных заменяются. Искать по контексту, не по именам.
